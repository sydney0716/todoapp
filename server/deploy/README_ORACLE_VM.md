# Oracle VM deployment and upgrades

The VM runs the API, PostgreSQL, Caddy for HTTPS, and backups. Build Flutter apps on your Mac. Revision `0c750be` was deployed on 2026-10-10 after a backup restore and migration rehearsal. The production upgrade preserved the existing tasks and subtasks, passed `/ready`, and retained database backups on the VM and Mac.

## Network and setup

Point a domain such as `todo.yourdomain.com` at the VM's public IP. Allow TCP 80 and 443 through the Oracle security rules and VM firewall; restrict SSH to your own IP. PostgreSQL remains private inside Docker; do not expose port 5432.

Install Docker Engine and the Compose plugin using [Docker's instructions for your OS](https://docs.docker.com/engine/install/). Verify `docker version` and `docker compose version`, then clone the repository on the VM:

```bash
git clone YOUR_PRIVATE_REPO_URL personal_todo
cd personal_todo
cp server/.env.example server/.env
```

Set the database credentials, `JWT_SECRET`, `USER1_PASSWORD`, `USER2_PASSWORD`, and `PERSONAL_TODO_DOMAIN` in `server/.env`. The account names are `user1` and `user2`. Use distinct account passwords and a long random JWT secret. Use a URL-safe database password, for example one generated by `openssl rand -hex 32`, because Compose constructs the SQLAlchemy connection URL from those credentials. Keep `AUTO_MIGRATE=false` and apply migrations explicitly. Never commit the environment file.

## First deployment

Run these commands from the repository root:

```bash
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml up -d postgres
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml build api
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml run --rm api python -m app.runtime_schema
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml up -d
curl --fail https://todo.yourdomain.com/ready
```

Expected response is `{"status":"ok"}`. `/ready` checks the database and required tables; `/health` only checks process liveness. Compose waits for database and API health before starting their dependents.

The migration command applies all SQL files in order, in one transaction, and records filenames in `schema_migrations`. It also works for an existing database whose migrations were applied manually. Do not replace or remove the `personaltodo_pgdata` volume.

## Upgrade an existing VM

Take a backup before changing the API or schema, and retain the previous code revision. Then stop API writes during the upgrade:

```bash
bash server/deploy/backup_postgres_docker.sh
git pull
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml stop api
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml build api
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml run --rm api python -m app.runtime_schema
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml up -d
curl --fail https://todo.yourdomain.com/ready
```

Do not continue after a failed backup or migration. Review logs with:

```bash
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml logs --tail=100 api
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml ps
```

This update adds migration `007_purged_tasks.sql` to retain purged IDs, including identifiable historical purge events, and `008_legacy_data_repair.sql` for the previous membership repair and completed-time backfill. Old completed tasks have no recoverable exact completion time, so the backfill uses their last update time. New completions receive the actual server acceptance time.

Update the server first, then update all four clients. Existing local databases upgrade to SQLite version 11 automatically without resetting task IDs or the offline queue. Older clients cannot provide the new pending-edit protections or follow `has_more`, so finish the client upgrade before relying on those fixes. Keep application IDs, signing identities, and app-group settings when installing over an existing app.

## Home Screen web app

Keep the API's port unpublished: the Compose configuration trusts forwarded client addresses from Caddy so login throttling can distinguish visitors. Caddy ignores client-supplied forwarded addresses by default. If you publish the API directly or add another proxy, configure explicit trusted proxies first.

For a hostname change, set `PERSONAL_TODO_DOMAIN` to the new hostname and temporarily set `PERSONAL_TODO_PREVIOUS_DOMAIN` to the old one. Point the new DNS record to the VM, recreate Caddy, and verify HTTPS. Native updates can include `TODO_PREVIOUS_API_BASE_URL` alongside `TODO_API_BASE_URL` in a gitignored build configuration to migrate a saved URL for the same backend while retaining sessions and cursors. Custom server URLs stay unchanged. Web storage belongs to each origin: sync pending edits at the old address, then open the new address, sign in, and add it to the Home Screen again. Clear the previous-domain setting and recreate Caddy after all devices have moved.

Build the static client on your Mac with Flutter 3.44 / Dart 3.12 or newer:

```bash
bash scripts/build_web.sh
```

Deploy the updated API and apply migrations first. Migration `009_web_device_platform.sql` allows `web` devices in the database; accepting `web` in the login schema alone is insufficient. Upload `build/web/` to `server/deploy/web/releases/BUILD_ID/` on the VM. This output includes the SQLite worker/Wasm files, local rendering/fonts, and the versioned offline shell cache. The two generated SQLite files under the source `web/` directory and deployed static files are gitignored.

On the VM, point `current` at that release and apply the updated Caddy configuration and Compose file:

```bash
ln -sfn releases/BUILD_ID server/deploy/web/current
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml up -d --no-deps caddy
curl --fail https://todo.yourdomain.com/app/manifest.json
curl --fail https://todo.yourdomain.com/ready
```

Caddy serves `/app/` and keeps the existing API routes at the domain root. The browser therefore uses the API on the same origin without opening cross-origin access. For later static-only updates, switch the `current` symlink after the upload completes; the stable parent-directory mount lets Caddy pick it up without restarting. Keep the previous release for rollback.

Install in Safari with Share → Add to Home Screen → Open as Web App. Tasks, settings, and queued edits persist in IndexedDB. The offline cache contains static app files only. Browser apps sync while open and on reopen; native widgets and scheduled reminders remain native-app features. Close all tabs and reopen the Home Screen app to activate an available web update.

## Backups, rotation, and off-VM copies

The Docker entrypoint uses the database container's PostgreSQL tools:

```bash
BACKUP_DIR="$HOME/personal_todo_backups" BACKUP_RETENTION_DAYS=30 bash server/deploy/backup_postgres_docker.sh
```

The script writes a temporary custom-format dump, verifies its archive listing, then renames it to a unique final filename. Failure leaves no partial final dump. Rotation runs only after a successful dump; leave `BACKUP_RETENTION_DAYS` unset to retain all backups. Archive-list validation is not a substitute for restoring the data.

For a host-installed PostgreSQL server, use `server/scripts/backup_postgres.sh` with `DATABASE_URL` exported and `pg_dump`/`pg_restore` on PATH. It accepts `postgresql+psycopg://` and handles URL-encoded credentials.

To schedule daily Docker backups, create the directory first and use `crontab -e`. Adapt this example to your actual VM username and clone path:

```cron
15 3 * * * cd /home/opc/personal_todo && BACKUP_DIR=/home/opc/personal_todo_backups BACKUP_RETENTION_DAYS=30 /usr/bin/bash server/deploy/backup_postgres_docker.sh >> /home/opc/personal_todo_backups/backup.log 2>&1
```

This is a suggested schedule; the repository does not install it. Verify the first scheduled backup and log. Copy backups off the VM regularly, for example from your Mac:

```bash
mkdir -p "$HOME/personal_todo_backups"
rsync -av opc@VM_PUBLIC_IP:~/personal_todo_backups/ "$HOME/personal_todo_backups/"
```

Off-VM copying is also manual unless you arrange a schedule. VM-local backups do not protect against losing the VM or its storage.

## Restore check in a separate database

Use a disposable database to verify a chosen dump without touching production. Replace the dump path below:

```bash
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml exec -T postgres sh -lc 'createdb -U "$POSTGRES_USER" personaltodo_restore_check'
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml exec -T postgres sh -lc 'pg_restore --exit-on-error --no-owner --no-privileges -U "$POSTGRES_USER" -d personaltodo_restore_check' < /path/to/personal_todo_backup.dump
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml exec -T postgres sh -lc 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d personaltodo_restore_check -c "SELECT count(*) FROM tasks; SELECT count(*) FROM subtasks; SELECT count(*) FROM purged_tasks;"'
```

Inspect representative task titles, deletion state, and subtasks as well as the counts. After inspection, remove only the disposable database:

```bash
docker compose --env-file server/.env -f server/deploy/docker-compose.oracle.yml exec -T postgres sh -lc 'dropdb -U "$POSTGRES_USER" personaltodo_restore_check'
```

An actual production restore requires stopping app writes and confirming the target database separately.

## Four-device release check

Use the same account on each person's phone and Mac. Configure the server on the initial login screen, or build with `--dart-define=TODO_API_BASE_URL=https://todo.yourdomain.com`.

1. Install over the existing apps and confirm tasks, subtasks, identities, and queued changes remain.
2. Take both users offline. Complete each half of a Both task and edit different fields/children. Reconnect in each order; both flags and edits should survive, with empty queues afterward.
3. Open an editor on one device, edit the note or add a child on another, then save only the first device's title. The partner's note/child should remain.
4. Create a task with children offline, trash it, and Undo before reconnecting. Check the children on the other devices.
5. Resume an idle app and confirm partner changes pull. Expire a refresh session and confirm the same-account login page opens automatically, retaining cached work and pending changes.
6. Check owner-only expired-trash purge. Reconnect an old offline client after purge and confirm the task does not reappear.
7. Schedule reminders on Android and iPhone; test denied permissions, Android reboot, and exact-alarm access. Test a Mac widget click with the main app closed.
8. Restore a recent backup into a separate database and confirm representative records. Check readiness after the upgrade.

Local automated checks and unsigned/debug builds are summarized in [README.md](../../README.md#review-and-verification). Signed Android and Apple Silicon macOS updates were installed over the existing apps on 2026-10-11, retaining their data storage. The updated Docker image and live deployment passed readiness checks. iPhone installation and the physical sync, notification, and widget checks above remain pending.
